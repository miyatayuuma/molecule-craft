# Reaction authority (T1)

`createReactionCatalogAuthority({polymerRoutes})` references the existing normal catalog and polymer route definitions. `get(id)`, `tags(id)`, `entries()`, `includedIds()` and `count()` expose the definition set, not a proven UI-reachable count. IDs are `normal:<catalog id>` and `polymer:<routeId>`. Tags can overlap; unclassified reactions have an empty tag array. UI should read molecule discovery separately from `collectionGame.state.hasMolecule(id)`; a known product is not proof of a reaction.

`collectionGame.reactionProgress` exposes `getState(id)`, `hint(id)`, `snapshot()` and `storageMessage`. `verified` takes precedence over `hinted`; callers should exclude both states from new hint drops. Production verification is connected only through validated normal product and completed finite PolymerSample events. Reference models, FEED and environment changes are not success events. New progress uses `molecule-craft.reaction-progress.v1`; legacy molecule data is never converted to reaction history. One-to-one legacy polymer discoveries are migrated from the existing polymer collection, whose production registration is called from the validated completed sample event. Unknown IDs in the new save are retained; unsupported schemas and concurrent writes are protected. Collection reset clears the new progress via the existing journal, while future schemas remain protected.

T2/T3 must account for the existing routing rule: the exact ethene-only Feed is owned by polyethylene and blocks the normal cyclobutane route. An extra species avoids exact ownership, but actual usability is unverified. Do not present 54 definitions as 54 currently reachable routes without resolving or assessing this conflict. UI selection/routing changes are outside T1.
